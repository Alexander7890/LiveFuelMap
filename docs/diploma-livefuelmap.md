# Розробка вебсервісу моніторингу цін на пальне з використанням вебскрапінгу та REST API

## 1. Вступ

У межах дипломного проєкту було розроблено вебсервіс **LiveFuelMap** - програмну систему для автоматизованого збору, збереження, аналізу та відображення актуальних цін на пальне в мережах автозаправних станцій. Система орієнтована на користувачів, яким необхідно швидко отримувати достовірну інформацію про вартість бензину, дизельного пального, газу та інших типів пального, а також на адміністраторів, які мають контролювати коректність даних, джерела отримання інформації, користувачів і статистику роботи сервісу.

LiveFuelMap поєднує декілька важливих підходів сучасної веброзробки: клієнтську SPA-архітектуру на React, серверну REST API-архітектуру на ASP.NET Core Web API, реляційну базу даних MySQL, автоматизований вебскрапінг зовнішніх джерел, систему авторизації на основі JWT, оновлення даних у реальному часі через SignalR, адміністративний інтерфейс, систему підписок і повідомлень, а також аналітичні модулі для перегляду історії зміни цін.

Основна ідея проєкту полягає в тому, щоб замінити ручний пошук цін на різних сайтах АЗС єдиною централізованою платформою. Користувач відкриває вебсервіс, обирає місто, тип пального або мережу АЗС, після чого отримує структуровану інформацію у вигляді карток, таблиць, графіків і статистичних показників. Дані оновлюються автоматично, а зміни цін можуть транслюватися на клієнтський інтерфейс без повного перезавантаження сторінки.

З технічної точки зору LiveFuelMap є повноцінною багаторівневою системою. Frontend відповідає за взаємодію з користувачем, маршрутизацію, візуалізацію даних, форми, фільтри та адаптивний інтерфейс. Backend реалізує бізнес-логіку, REST API, авторизацію, роботу з базою даних, скрапінг, логування, обробку помилок і real-time оновлення. База даних зберігає користувачів, АЗС, типи пального, ціни, історію зміни цін, підписки, коментарі, токени, джерела даних і журнали виконання парсера.

## 2. Актуальність теми

Ціни на пальне є важливим економічним показником, який безпосередньо впливає на витрати приватних водіїв, логістичних компаній, служб доставки, підприємств з власним автопарком і загалом на транспортну інфраструктуру. Вартість бензину, дизельного пального та автогазу змінюється під впливом валютного курсу, податків, вартості нафти, логістики, регіональних факторів, політики окремих мереж АЗС і ринкової конкуренції.

Проблема полягає в тому, що користувачеві часто потрібно перевіряти ціни на різних сайтах, у мобільних застосунках окремих мереж або в неструктурованих джерелах. Такий підхід є незручним, повільним і не завжди дає повну картину ринку. Крім того, ціни можуть змінюватися щоденно або навіть частіше, тому ручне оновлення інформації не забезпечує достатньої актуальності.

Відсутність централізованого сервісу з актуальними цінами створює інформаційний розрив між водіями та ринком. Користувач не завжди знає, де дешевше заправитися, як змінилася ціна за останні дні, яка мережа пропонує найнижчу або найстабільнішу вартість, і чи варто обирати іншу АЗС. Для вирішення цієї проблеми доцільним є використання автоматизованого збору даних, збереження історії цін та візуального аналізу.

Вебскрапінг у цьому контексті є практично значущим інструментом, оскільки дозволяє автоматично отримувати інформацію з відкритих вебджерел, очищати її, нормалізувати та завантажувати до власної бази даних. REST API забезпечує стандартизований доступ до цих даних для frontend-частини, адмін-панелі, мобільного застосунку або сторонніх сервісів. Система реального часу підвищує інтерактивність сервісу, оскільки користувач може бачити оновлення без ручного оновлення сторінки.

Таким чином, тема дипломного проєкту є актуальною з практичної та інженерної точки зору, оскільки поєднує роботу з даними, backend-архітектуру, frontend-розробку, безпеку, автоматизацію, аналітику та сучасні web-технології.

## 3. Мета та завдання проєкту

Метою проєкту є розробка вебсервісу LiveFuelMap для автоматизованого моніторингу цін на пальне, який забезпечує збір даних із зовнішніх джерел, їх збереження в реляційній базі даних, надання доступу через REST API, візуалізацію у вебінтерфейсі, оновлення в реальному часі та адміністрування даних.

Для досягнення мети були поставлені такі завдання:

1. Проаналізувати предметну область моніторингу цін на пальне та визначити основні сутності системи: користувач, АЗС, тип пального, ціна, джерело даних, підписка, повідомлення, роль, токен.
2. Спроєктувати багаторівневу архітектуру з розділенням на frontend, API-рівень, бізнес-логіку, доступ до даних та інфраструктурні сервіси.
3. Реалізувати backend на ASP.NET Core Web API з підтримкою REST API, JWT-авторизації, role-based access control, middleware, dependency injection, логування та обробки помилок.
4. Реалізувати базу даних на MySQL з використанням Entity Framework Core, міграцій, зв'язків між таблицями, індексів і нормалізованої структури.
5. Реалізувати автоматизований вебскрапінг джерел цін, нормалізацію назв АЗС і типів пального, перевірку валідності даних та збереження історії зміни цін.
6. Реалізувати frontend на React, Vite і Tailwind CSS з адаптивним дизайном, маршрутизацією, компонентною архітектурою, таблицями, картками, графіками, фільтрами та модальними вікнами.
7. Реалізувати оновлення даних у реальному часі через SignalR/WebSocket, щоб користувацький інтерфейс міг реагувати на зміну цін без перезавантаження сторінки.
8. Реалізувати систему авторизації, реєстрації, email-верифікації, refresh-токенів, профілю користувача, підписок і повідомлень.
9. Реалізувати адмін-панель для керування користувачами, АЗС, цінами, джерелами даних, API-токенами, коментарями та запуском парсера.
10. Провести тестування основних модулів, включно з unit-тестами та integration-тестами API.
11. Підготувати систему до розгортання з використанням Docker Compose, конфігурацій середовища та документації.

## 3.1. Постановка задачі

У межах дипломного проєкту поставлено задачу створення вебсервісу LiveFuelMap, який забезпечує повний цикл роботи з даними про ціни на пальне: автоматизоване отримання інформації із зовнішніх джерел, очищення та нормалізацію даних, збереження в реляційній базі даних, надання доступу через REST API, відображення у вебінтерфейсі, оновлення в реальному часі, адміністрування та аналітичну обробку.

**Вхідними даними системи** є:

- HTML або JSON-дані зовнішніх джерел, що містять назви АЗС, типи пального, ціни, дату актуальності, регіон або місто;
- дані, введені користувачем через frontend: параметри фільтрації, пошукові запити, дані реєстрації, дані профілю, коментарі, підписки, повідомлення чат-боту;
- адміністративні дані: створення або редагування АЗС, ручні корекції цін, керування джерелами даних, ролями користувачів та API-токенами;
- службові дані конфігурації: connection string до MySQL, JWT secret, параметри парсера, параметри rate limiting, адреса SignalR Hub, налаштування локального AI.

**Вихідними даними системи** є:

- структурований список АЗС з актуальними цінами;
- історія зміни цін за обраний період;
- графіки та статистичні показники;
- JSON-відповіді REST API;
- real-time повідомлення про зміну цін через SignalR;
- експортовані звіти;
- повідомлення користувачу про підписки та зміни;
- відповіді чат-помічника на природномовні запити;
- адміністративні журнали запусків парсера, метрики API та результати керування даними.

**Користувачами системи** є:

- гість, який переглядає публічні ціни, фільтрує АЗС, користується пошуком, графіками та чат-помічником;
- авторизований користувач, який додатково керує профілем, підписками, коментарями та персональними сценаріями;
- адміністратор, який керує користувачами, АЗС, джерелами даних, цінами, коментарями, API-токенами та запуском парсера;
- зовнішній сервіс або інтеграційний клієнт, який отримує дані через API-токен зі scope-доступом.

**Обмеження задачі**:

- система працює з тими джерелами, для яких налаштовано парсер або API-клієнт;
- актуальність цін залежить від актуальності зовнішніх джерел і частоти запуску парсера;
- зміна HTML-структури зовнішнього сайту потребує оновлення відповідного parser client;
- локальна AI-модель використовується як допоміжний мовний шар, а фактичні ціни беруться з бази даних;
- доступ до адміністративних функцій обмежено роллю `Admin`;
- історія чат-помічника обмежується останніми повідомленнями сесії, щоб не перевантажувати AI-контекст.

**Основні сценарії роботи системи**:

1. Користувач відкриває LiveFuelMap, обирає місто та тип пального, після чого отримує список АЗС з актуальними цінами.
2. Користувач сортує АЗС за ціною, переглядає картки, таблиці та графіки історії.
3. Авторизований користувач створює підписку на зміну ціни для конкретного міста і типу пального.
4. Адміністратор запускає парсер вручну або очікує автоматичного фонового запуску.
5. Парсер отримує дані із зовнішнього джерела, нормалізує їх і зберігає нові записи в MySQL.
6. Якщо ціна змінилася, backend формує подію та надсилає її клієнтам через SignalR.
7. Користувач ставить запитання чат-помічнику, наприклад про ціну А-95 на конкретній АЗС, а система формує відповідь на основі БД і контексту поточної сесії.

- система реалізує автоматичний вебскрапінг;
- система реалізує ручний запуск парсера адміністратором;
- система реалізує реєстрацію, вхід, вихід, refresh token та email-верифікацію;
- система реалізує профіль користувача, редагування та видалення профілю;
- система реалізує підписки на оновлення;
- система реалізує коментарі та оцінки;

- система реалізує API-токени для стороннього доступу;

- система реалізує експорт звітів.

**Нефункціональні вимоги**:

- система побудована за багаторівневою архітектурою з розділенням API, BLL, DAL та Infrastructure;
- система використовує асинхронну обробку HTTP-запитів і запитів до БД;
- система має бути підтримуваною, тестованою та готовою до розширення;
- frontend має працювати як SPA і не перезавантажувати сторінку при зміні маршрутів;
- backend має повертати стабільні DTO-контракти;
- система має підтримувати локальний запуск і Docker Compose-сценарій;
- конфігурація має зберігатися окремо від коду.

**Вимоги до безпеки**:

- паролі зберігаються тільки у вигляді BCrypt-хешу;
- API захищено JWT access token;
- довготривала сесія працює через refresh token;
- адміністративні endpoint-и доступні тільки ролі `Admin`;
- сторонній API-доступ працює через API-токени зі scope-обмеженнями;
- write-запити захищені idempotency-механізмом;
- API обмежується rate limiting;
- чат-помічник захищений від prompt injection і запитів на службову інформацію;
- вхідні дані проходять валідацію та нормалізацію.

**Вимоги до продуктивності**:

- списки даних завантажуються з пагінацією та серверною фільтрацією;
- для читання використовуються оптимізовані EF Core-запити;
- у БД створено індекси для email, nickname, refresh token, station normalized key, fuel code, price history, subscriptions, chat history та parser runs;
- SignalR передає події зміни, а не великі масиви даних;
- історія чат-помічника обмежується останніми повідомленнями;
- frontend завантажує дані через централізований API-шар і оновлює тільки потрібні компоненти.

**Вимоги до інтерфейсу**:

- інтерфейс реалізовано адаптивним для desktop і mobile;
- основні сценарії доступні з головної сторінки;
- картки АЗС, таблиці, графіки, фільтри та модальні вікна мають єдину візуальну систему;
- користувач отримує toast-повідомлення про успішні дії та помилки;
- адмін-панель має таблиці, пошук, фільтрацію та дії керування;
- чат-помічник доступний з інтерфейсу та підтримує прокручування історії повідомлень.

## 4. Опис предметної області

Предметною областю є моніторинг цін на пальне в мережах автозаправних станцій. Основними об'єктами цієї області є АЗС, типи пального, актуальні ціни, історія зміни цін, джерела отримання даних, користувачі та підписки на оновлення.

АЗС у системі описується назвою мережі, нормалізованим ключем, адресою, містом, координатами, фото, вебсайтом та ознакою активності. Тип пального описується кодом і назвою. Для стабільної роботи API використовуються не випадкові числові ідентифікатори, а зрозумілі коди: `a95plus`, `a95`, `a92`, `diesel`, `gas`. Це дозволяє frontend-частині, API та парсеру однаково трактувати типи пального.

Ціна пального є часовим записом, пов'язаним з конкретною АЗС, конкретним типом пального, датою, джерелом і значенням ціни. Збереження кожного нового запису за датою дозволяє формувати історію зміни цін, будувати графіки, порівнювати поточні та попередні значення, визначати тенденції та відсоток зміни.

Користувачі можуть переглядати ціни, авторизуватися, редагувати профіль, залишати коментарі, створювати підписки на оновлення, отримувати повідомлення та працювати з персональним кабінетом. Адміністратор має розширені права: керування користувачами, джерелами даних, АЗС, цінами, коментарями, API-токенами та ручним запуском парсера.

## 5. Загальний опис вебсервісу LiveFuelMap

LiveFuelMap є вебсервісом, який надає користувачу єдину точку доступу до актуальної інформації про пальне. Сервіс працює за таким принципом: backend періодично запускає фоновий парсер, отримує дані із зовнішніх джерел, перетворює їх у внутрішній формат, перевіряє валідність, нормалізує назви АЗС і пального, зберігає записи в базу даних, після чого через REST API та SignalR передає інформацію frontend-частині.

Користувач бачить інтерактивний інтерфейс із картками АЗС, таблицями цін, фільтрами, пошуком, сортуванням, графіками та статистикою. Якщо ціна змінюється, система надсилає оновлення через real-time канал, а frontend оновлює відповідні елементи без перезавантаження сторінки.

Окремою частиною системи є адмін-панель. Вона використовується для контролю даних, перегляду користувачів, редагування ролей, модерації коментарів, керування АЗС, створення API-токенів, перегляду метрик, контролю джерел і запуску парсера. Це дозволяє підтримувати якість даних навіть у випадках, коли автоматичний скрапінг потребує ручної перевірки.

## 5.1. Опис реалізованого функціоналу особисто

У межах дипломного проєкту особисто реалізовано повний full-stack цикл розробки вебсервісу LiveFuelMap. Реалізація охоплює frontend-частину, backend API, базу даних, модулі вебскрапінгу, систему авторизації, адміністративну панель, аналітичні елементи, систему повідомлень, чат-помічник і тестування.

На frontend-рівні створено React/Vite SPA-застосунок з компонентною архітектурою. Реалізовано головну сторінку, картки АЗС, таблиці цін, графіки, фільтри, пошук, сортування, профіль користувача, модальні вікна авторизації, панель підписок, коментарі, адмін-панель і чат-віджет. Інтерфейс стилізовано за допомогою Tailwind CSS, адаптовано під desktop і mobile, додано анімації, toast-повідомлення та централізований API-сервіс для взаємодії з backend.

На backend-рівні реалізовано ASP.NET Core Web API з контролерами для станцій, пального, історії цін, авторизації, профілю, підписок, коментарів, звітів, адміністративних дій, API-токенів, зовнішнього API та чат-бота. Реалізовано JWT-авторизацію, refresh token, BCrypt-хешування паролів, email-верифікацію, role-based authorization, API-token authentication, rate limiting, idempotency middleware, request logging, API metrics та SignalR Hub.

На рівні бази даних створено модель даних у MySQL через Entity Framework Core. Реалізовано сутності `User`, `Station`, `Fuel`, `FuelPrice`, `Subscription`, `Comment`, `ApiToken`, `ChatMessage`, `DataSource`, `ParserRun`, `ApplicationLog`, зв'язки між ними, індекси, міграції та seed-дані для довідників і тестових сценаріїв.

Для автоматичного збору даних реалізовано фоновий worker вебскрапінгу. Він завантажує активні джерела, створює журнал запуску парсера, отримує HTML або JSON, перетворює дані у внутрішні записи, нормалізує назви АЗС і типи пального, перевіряє дублювання, порівнює старі й нові ціни, зберігає історію та надсилає повідомлення про зміни через SignalR.

Окремо реалізовано чат-помічник як додатковий модуль інтелектуальної взаємодії, а не як ядро системи. Він зберігає історію діалогу за `SessionId` і `UserId`, визначає intent користувача, нормалізує пальне та назви АЗС, використовує контекст попередніх повідомлень, формує прямі відповіді з БД, ставить уточнюючі питання при нестачі параметрів, обмежує тематику запитів і інтегрується з локальною AI-моделлю через Ollama.

Також реалізовано unit та integration tests, які перевіряють авторизацію, безпеку адмін-доступу, публічні контролери, роботу чат-історії, нормалізацію пального, імпорт цін, BCrypt, JWT signing key, parser client і логіку визначення змін цін.

## 5.2. Обмеження реалізованої системи

LiveFuelMap реалізовано як дипломний full-stack вебсервіс з production-ready архітектурними підходами, однак система має об'єктивні технічні обмеження, які враховано в проєктуванні.

Перше обмеження пов'язане із зовнішніми джерелами. Вебскрапінг залежить від доступності сайтів, швидкості їх відповіді, стабільності HTML-структури та коректності опублікованих даних. Якщо зовнішній сайт змінює структуру таблиці або блоку цін, відповідний parser client потребує оновлення.

Друге обмеження стосується актуальності даних. Система оновлює ціни за розкладом або за ручним запуском адміністратора, тому між фактичною зміною ціни на АЗС і появою нового запису в LiveFuelMap існує часовий інтервал. Для зменшення цього обмеження реалізовано журнал запусків парсера, контроль джерел і real-time повідомлення після збереження змін.

Третє обмеження пов'язане з локальною AI-моделлю. Локальний AI через Ollama є безкоштовним і зручним для дипломного проєкту, але якість генерації залежить від обраної моделі та ресурсів комп'ютера. Тому фактичні ціни не генеруються AI-моделлю: backend спочатку отримує дані з БД, а AI використовується лише як мовний шар для формування відповіді.

Четверте обмеження стосується масштабування real-time каналу. У локальній реалізації SignalR працює в межах одного API-інстансу. Для горизонтального масштабування на декілька серверів у production потрібно додати backplane, наприклад Redis, щоб події синхронізувалися між інстансами.

П'яте обмеження пов'язане з обсягом історичних даних. Історія цін зростає з кожним запуском парсера. У системі реалізовано індексацію та retention-параметри парсера, а для великого production-обсягу даних передбачено подальше архівування або партиціювання таблиць за датою.

## 7. Архітектура системи

Архітектура LiveFuelMap побудована за багаторівневим принципом. Такий підхід дозволяє розділити відповідальність між різними частинами системи, спростити тестування, підтримку та майбутнє масштабування.

Основні рівні системи:

1. **Frontend-рівень** - React/Vite застосунок, який відповідає за користувацький інтерфейс, маршрутизацію, форми, фільтри, графіки, модальні вікна, адаптивність і взаємодію з API.
2. **API-рівень** - ASP.NET Core Web API, який приймає HTTP-запити, виконує авторизацію, перевіряє права доступу, викликає бізнес-сервіси та повертає DTO-відповіді.
3. **BLL-рівень** - бізнес-логіка, де реалізовано роботу з цінами, користувачами, профілями, підписками, звітами, чат-ботом, імпортом даних і перевіркою змін.
4. **DAL-рівень** - Entity Framework Core, DbContext, сутності, репозиторії, Unit of Work і міграції бази даних.
5. **Infrastructure-рівень** - інфраструктурні сервіси: JWT, BCrypt-хешування, email, логування, парсинг, HTTP-клієнти джерел, фоновий worker, інтеграції з AI та зовнішніми сервісами.
6. **Database-рівень** - MySQL, де зберігаються дані системи.
7. **Real-time-рівень** - SignalR Hub, який забезпечує двосторонній канал між сервером і клієнтом.

Типовий потік даних виглядає так: фоновий worker запускає парсер, парсер отримує дані із зовнішнього сайту, сервіс імпорту очищає та нормалізує записи, EF Core зберігає їх у MySQL, backend формує DTO, frontend отримує дані через REST API, а при зміні цін SignalR надсилає подію клієнтам.

## 8. Frontend-частина

Frontend-частина LiveFuelMap реалізована як SPA-застосунок на **React**. React - це JavaScript-бібліотека для побудови користувацьких інтерфейсів на основі компонентів. Вона була обрана через високу продуктивність, велику екосистему, зрозумілу модель стану, підтримку повторного використання компонентів і зручну інтеграцію з REST API та real-time каналами.

Для збирання frontend-застосунку використовується **Vite**. Vite - це сучасний build tool, який забезпечує швидкий запуск dev-сервера, миттєве оновлення модулів під час розробки та оптимізовану production-збірку. На відміну від старіших інструментів, Vite використовує нативні ES-модулі в режимі розробки, тому значно прискорює робочий процес.

Для стилізації використовується **Tailwind CSS**. Tailwind CSS - це utility-first CSS-фреймворк, який дозволяє створювати адаптивний інтерфейс без написання великої кількості окремих CSS-класів. Його перевага для LiveFuelMap полягає в тому, що картки АЗС, таблиці, фільтри, модальні вікна та адмін-панель стилізовано в єдиній системі відступів, кольорів, адаптивних breakpoint-ів і станів.

Маршрутизація реалізована за допомогою **React Router**. React Router дозволяє створити набір сторінок без повного перезавантаження браузера: головна сторінка, сторінка звітів, адмін-панель, сторінки профілю та інші розділи. SPA-підхід покращує швидкість взаємодії, оскільки після початкового завантаження застосунок змінює тільки потрібні компоненти.

HTTP-взаємодія з backend виконується через централізований API-шар. У сучасних React-проєктах для цього часто використовують **Axios** або стандартний **Fetch API**. Axios - це HTTP-клієнт, який спрощує роботу із запитами, заголовками, interceptors та обробкою помилок. У LiveFuelMap клієнтський API-рівень реалізовано централізовано у вигляді сервісу, який виконує ті самі архітектурні функції: формує URL, додає JWT-заголовки, обробляє 401-відповіді, автоматично оновлює access token через refresh token, читає JSON або файли та уніфіковано повертає помилки.

Для real-time взаємодії використовується пакет **@microsoft/signalr**. SignalR у браузері встановлює підключення до hub-адреси `/hubs/fuel`, підтримує автоматичне перепідключення і передає access token для захищених сценаріїв. Це дозволяє frontend-частині реагувати на події зміни цін, оновлювати таблиці, картки та повідомлення без ручного оновлення сторінки.

Структура frontend побудована компонентно:

- `components/common` - спільні UI-компоненти, кнопки, теми, бренд-елементи;
- `components/stations` - картки АЗС, карусель, відображення мереж;
- `components/fuel` - графіки, калькулятор, порівняння станцій;
- `components/profile` - профіль, авторизаційні модальні вікна, підписки;
- `components/comments` - коментарі й оцінки;
- `components/chat` - чат-бот;
- `contexts` - глобальні контексти авторизації, даних і toast-повідомлень;
- `services` - API-клієнт і SignalR-клієнт;
- `pages` - сторінки застосунку;
- `hooks` - повторно використовувана логіка, наприклад плавний скрол.

Система стану реалізована через React Context. `AuthContext` зберігає стан авторизації, токени та користувача. `DataContext` централізує завантаження базових даних. `ToastContext` відповідає за повідомлення користувачу. Для зберігання access token і refresh token використовується `localStorage`, що дозволяє зберігати сесію після перезавантаження сторінки. При цьому backend перевіряє строк дії токенів і token version, тому відкликання токенів залишається контрольованим на сервері.

Адаптивність реалізована за mobile-first підходом. Інтерфейс спроєктовано так, щоб основні сценарії були доступні на смартфонах, планшетах і desktop-екранах. Таблиці мають компактне відображення, картки перебудовуються за шириною екрана, модальні вікна не виходять за межі viewport, а кнопки та поля мають достатню площу натискання.

Анімації реалізовані за допомогою **Framer Motion**, **GSAP** і допоміжних motion-компонентів. Анімації використовуються не як декоративний надлишок, а для покращення UX: плавне відкриття модальних вікон, поява карток, переходи між станами, індикатори завантаження. Це робить інтерфейс більш зрозумілим, оскільки користувач бачить причинно-наслідковий зв'язок між дією та результатом.

## 9. Backend-частина

Backend LiveFuelMap реалізований на **ASP.NET Core Web API** мовою **C#**. ASP.NET Core - це кросплатформовий високопродуктивний фреймворк для створення вебзастосунків, API, real-time сервісів і фонового виконання задач. C# було обрано через строгий типізований підхід, розвинену екосистему .NET, якісну підтримку асинхронного програмування, dependency injection, Entity Framework Core, SignalR, middleware та enterprise-практики безпеки.

Backend має модульну структуру:

- `LiveFuelMap.Api` - контролери, SignalR Hub, Swagger, middleware, authentication, конфігурація застосунку;
- `LiveFuelMap.BLL` - DTO, інтерфейси, бізнес-сервіси, імпорт цін, профілі, звіти, чат, валідація;
- `LiveFuelMap.DAL` - сутності, DbContext, міграції, репозиторії, Unit of Work;
- `LiveFuelMap.Infrastructure` - JWT, BCrypt, email, логування, парсинг, worker, AI-клієнти, зовнішні сервіси;
- `LiveFuelMap.Tests` - unit та integration тести.

REST API реалізовано через контролери ASP.NET Core. Контролер відповідає за прийняття HTTP-запиту, перевірку моделі, авторизацію, виклик відповідного сервісу та повернення результату. Бізнес-логіка не розміщується безпосередньо у контролерах, що є важливою архітектурною перевагою: контролери залишаються тонкими, а сервіси можна тестувати незалежно.

Для впровадження залежностей використовується **Dependency Injection**. DI дозволяє реєструвати сервіси, репозиторії, DbContext, логери, email-сервіси, парсери та інші компоненти у контейнері залежностей. Це зменшує зв'язаність коду, спрощує тестування та дозволяє замінювати реалізації без зміни споживачів.

У backend застосовано **Repository Pattern** і **Unit of Work**. Репозиторії інкапсулюють доступ до таблиць, а Unit of Work координує збереження змін у межах транзакційного сценарію. Це відокремлює бізнес-логіку від деталей EF Core і дозволяє централізовано керувати запитами до бази даних.

Middleware використовується для наскрізних задач: логування запитів, метрик API, rate limiting, idempotency, автентифікації, авторизації та обробки статичних файлів. Така модель дозволяє виконувати спільну логіку для всіх endpoint-ів без дублювання коду в контролерах.

## 10. База даних

У поточній реалізації LiveFuelMap використовується **MySQL 8**. MySQL - це реляційна СУБД, яка добре підходить для структурованих даних, транзакційних операцій, індексації, зв'язків між таблицями та аналітичних запитів середньої складності. Для дипломного проєкту MySQL є доцільним вибором через простоту розгортання, підтримку Docker, сумісність з EF Core та достатню продуктивність.

У реалізованому проєкті використано **MySQL**. PostgreSQL розглянуто як можливу альтернативу для майбутньої геоаналітики, JSONB-сценаріїв і PostGIS, проте поточна реалізація LiveFuelMap повністю працює на MySQL і використовує EF Core migrations для керування схемою.

Основні таблиці:

- `Users` - користувачі, email, хеш пароля, роль, профіль, email verification, refresh token, token version;
- `Stations` - АЗС, назва, нормалізований ключ, адреса, місто, координати, фото, сайт, активність;
- `Fuels` - типи пального з кодами `a95plus`, `a95`, `a92`, `diesel`, `gas`;
- `FuelPrices` - записи цін за станцією, пальним, датою, джерелом і значенням;
- `Subscriptions` - підписки користувачів на тип пального і місто;
- `Comments` - коментарі та оцінки АЗС;
- `ApiTokens` - токени для зовнішнього API-доступу;
- `ChatMessages` - історія повідомлень чат-бота в межах session/user context;
- `DataSources` - джерела парсингу;
- `ParserRuns` - журнал запусків парсера;
- `ApplicationLogs` - приклад таблиці для логування подій.

Зв'язки між таблицями побудовані за реляційною моделлю. Один користувач може мати багато підписок, коментарів, API-токенів і повідомлень чату. Одна АЗС має багато записів цін і коментарів. Один тип пального має багато записів цін і підписок. `FuelPrice` зв'язує `Station` і `Fuel`, тому історія цін формується як набір записів для конкретної пари АЗС-пальне на конкретну дату.

Нормалізація даних зменшує дублювання. Назва типу пального не повторюється у кожному записі ціни, а зберігається в таблиці `Fuels`. Назва АЗС, адреса та координати зберігаються в `Stations`, а ціна посилається на станцію через зовнішній ключ. Це забезпечує цілісність даних і спрощує зміну довідникової інформації.

Для оптимізації SQL-запитів у моделі БД використано індекси за email, nickname, refresh token, `NormalizedKey + City`, `City`, `Fuel.Code`, `StationId + FuelId + Date`, `FuelId + Date`, `UserId + FuelId + City + Frequency`, `SessionId + CreatedAt`, `UserId + CreatedAt` та `SourceId + StartedAt`. Найчастіші запити системи - отримання останньої ціни за типом пального, історії за період, списку АЗС у місті та пошук за нормалізованим ключем. Індексація зменшує час виконання таких запитів і знижує навантаження на БД.

## 11. Вебскрапінг

Вебскрапінг у LiveFuelMap реалізує автоматичний збір даних із зовнішніх джерел. Його роль полягає в тому, щоб отримувати актуальні ціни без ручного введення адміністратором. Це особливо важливо для сервісу моніторингу цін, оскільки актуальність даних є основною цінністю системи.

Скрапінг працює через фоновий `BackgroundService`. Worker запускається за конфігурованим інтервалом, отримує список активних джерел з таблиці `DataSources`, для кожного джерела створює відповідний клієнт, завантажує HTML або JSON, перетворює дані у внутрішні `FuelPriceRecord`, після чого передає записи до сервісу імпорту.

Сервіс імпорту виконує декілька етапів:

1. Перевіряє валідність запису: наявність назви АЗС, типу пального, ціни, дати.
2. Нормалізує тип пального: наприклад, `95`, `А-95`, `A95` перетворюються на `a95`; `ДП`, `ДТ`, `diesel` - на `diesel`; `газ`, `LPG` - на `gas`.
3. Нормалізує назву АЗС: прибирає зайві символи, враховує різні варіанти написання, формує стабільний ключ.
4. Знаходить наявну станцію або створює нову, якщо вона раніше не існувала.
5. Перевіряє, чи є запис ціни за поточну дату.
6. Якщо запис існує і ціна змінилася, оновлює його або створює нову точку історії відповідно до логіки.
7. Порівнює нову ціну з попередньою та визначає тип зміни.
8. Зберігає зміни в БД.
9. Формує повідомлення для real-time оновлення клієнтів.

Захист від дублювання реалізується через перевірку комбінації `StationId + FuelId + Date`. Це запобігає створенню декількох однакових записів за один день. Якщо ціна змінилася, система фіксує оновлення та формує подію зміни.

Кожен запуск парсера зберігається у `ParserRuns`. Там фіксуються час старту, час завершення, статус, кількість знайдених записів, кількість збережених записів, помилка та тривалість. Це важливо для адміністрування: адміністратор може бачити, чи працюють джерела, які з них падають, чи зменшилася кількість записів і коли був останній успішний запуск.

## 12. REST API

REST API є центральним способом взаємодії між frontend і backend. REST - це архітектурний стиль, у якому ресурси системи доступні через URL, а операції виконуються стандартними HTTP-методами: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.

У LiveFuelMap API виконує такі функції:

- `GET /api/stations` - отримання списку АЗС з фільтрами;
- `POST /api/stations` - створення АЗС адміністратором;
- `PUT /api/stations/{id}` - редагування АЗС;
- `DELETE /api/stations/{id}` - видалення або деактивація АЗС;
- `GET /api/fuels` - отримання типів пального;
- `GET /api/fuel-prices/history` - отримання історії цін;
- `POST /api/fuel-prices/corrections` - ручна корекція ціни;
- `POST /api/auth/register` - реєстрація;
- `POST /api/auth/login` - вхід;
- `POST /api/auth/refresh` - оновлення access token;
- `POST /api/auth/logout` - вихід;
- `POST /api/auth/verify-email` - підтвердження email;
- `GET /api/profile` - отримання профілю;
- `PUT /api/profile` - редагування профілю;
- `DELETE /api/profile` - видалення профілю;
- `GET /api/subscriptions` - список підписок;
- `POST /api/subscriptions` - створення підписки;
- `DELETE /api/subscriptions/{id}` - видалення підписки;
- `GET /api/admin/users` - керування користувачами;
- `GET /api/admin/data-sources` - керування джерелами;
- `POST /api/admin/data-sources/parser/run` - ручний запуск парсера;
- `GET /api/external/current-prices` - API для сторонніх сервісів через API-токен;
- `POST /api/reports/fuel-prices/export` - експорт звіту.

Для передачі даних використовуються **DTO**. DTO відокремлюють внутрішню структуру сутностей бази даних від зовнішнього API-контракту. Це важливо для безпеки й стабільності: frontend не повинен отримувати пароль, хеші токенів або службові поля. DTO також дозволяють змінювати базу даних без руйнування API-контрактів.

Коди відповідей HTTP використовуються відповідно до призначення: `200 OK` для успішного отримання, `201 Created` для створення, `204 No Content` для видалення без тіла відповіді, `400 Bad Request` для помилок валідації, `401 Unauthorized` для відсутньої автентифікації, `403 Forbidden` для недостатніх прав, `404 Not Found` для відсутнього ресурсу, `409 Conflict` для конфліктів, `429 Too Many Requests` для rate limiting і `500 Internal Server Error` для непередбачених помилок.

## 13. Авторизація та безпека

Система авторизації LiveFuelMap побудована на **JWT**. JWT, або JSON Web Token, - це компактний підписаний токен, який містить claims про користувача: ідентифікатор, роль, версію токена, строк дії. Backend видає access token після успішного входу, а frontend додає його в заголовок `Authorization: Bearer <token>`.

Переваги JWT для LiveFuelMap:

- API не зобов'язаний зберігати серверну сесію для кожного запиту;
- токен можна використовувати у SPA, SignalR і мобільному застосунку;
- роль користувача може бути включена у claims;
- строк дії access token обмежує ризики у випадку викрадення;
- refresh token дозволяє поновлювати сесію без повторного входу.

Refresh token зберігається окремо та може бути відкликаний. У користувача є поле `TokenVersion`; якщо адміністратор змінює роль, блокує користувача або потрібно відкликати старі токени, token version збільшується. Під час валідації JWT backend перевіряє, чи збігається token version у токені з актуальним значенням у базі даних. Це дозволяє відкликати токени навіть до завершення строку їх дії.

Паролі не зберігаються у відкритому вигляді. Для хешування використовується **BCrypt**. BCrypt спеціально створений для захисту паролів: він повільніший за криптографічні хеші загального призначення, підтримує salt і параметр складності. Це ускладнює brute-force атаки у випадку витоку бази даних.

Role-based authorization реалізує дві основні ролі: `User` і `Admin`. Звичайний користувач може переглядати дані, керувати профілем, підписками та коментарями. Адміністратор має доступ до адміністративних endpoint-ів, джерел даних, користувачів, API-токенів, ручного запуску парсера та корекції цін. Політика `AdminOnly` на backend гарантує, що навіть якщо користувач вручну відкриє admin route на frontend, API не дозволить виконати захищену операцію.

Для email-верифікації система генерує код або токен підтвердження, зберігає його хеш і строк дії, після чого надсилає лист користувачу. Зберігання саме хешу токена зменшує ризики: навіть якщо база буде скомпрометована, реальний verification token не буде доступний у відкритому вигляді.

Додаткові засоби безпеки:

- rate limiting для обмеження кількості запитів;
- idempotency key для захисту від повторного виконання чутливих POST-запитів;
- CORS-конфігурація;
- валідація вхідних моделей;
- перевірка ролей на endpoint-ах;
- API-токени зі scopes для сторонніх сервісів;
- логування підозрілих або помилкових запитів;
- обмеження довжини повідомлень у чаті;
- захист від витоку системного prompt-а та службової інформації.

## 14. Система реального часу

Для роботи в реальному часі використовується **SignalR**. SignalR - це бібліотека Microsoft для двосторонньої комунікації між сервером і клієнтом. Вона використовує WebSocket, якщо він доступний, або fallback-механізми в інших середовищах.

WebSocket - це протокол, який дозволяє встановити постійне двостороннє з'єднання між браузером і сервером. На відміну від класичних HTTP-запитів, клієнту не потрібно постійно опитувати сервер. Сервер сам може надіслати подію, коли дані змінилися.

У LiveFuelMap SignalR використовується для:

- сповіщення клієнтів про зміну цін;
- оновлення таблиць і карток АЗС;
- зменшення кількості зайвих HTTP-запитів;
- підвищення інтерактивності;
- синхронізації декількох відкритих клієнтів;
- передачі push-подій після успішного імпорту нових цін.

Після завершення роботи парсера сервіс імпорту формує список змін. Якщо зміни є, notifier надсилає подію до SignalR Hub. Frontend має активне підключення і отримує подію, після чого може оновити локальний стан або повторно завантажити потрібні дані через REST API. Така комбінація REST API та SignalR є практичною: REST використовується для отримання повних ресурсів, а SignalR - для повідомлення про зміну стану.

## 15. Адмін-панель

Адмін-панель LiveFuelMap призначена для підтримки коректності даних і керування системою. Вона доступна лише користувачам з роллю `Admin`. Навіть якщо frontend приховує адмін-інтерфейс для звичайних користувачів, основний захист реалізований на backend через role-based authorization.

Функції адмін-панелі:

- перегляд користувачів;
- зміна ролей користувачів;
- видалення користувачів;
- модерація коментарів;
- перегляд і видалення коментарів;
- створення, редагування та видалення АЗС;
- ручна корекція цін;
- перегляд API-метрик;
- керування API-токенами;
- створення API-токенів зі scopes;
- відкликання API-токенів;
- перегляд джерел даних;
- перегляд журналу запусків парсера;
- ручний запуск парсера.

Адмін-панель використовує таблиці з пошуком, фільтрами та сортуванням. Для критичних дій використовуються підтвердження, щоб зменшити ризик випадкового видалення або зміни важливих даних. Усі зміни проходять через API, тому backend може виконувати валідацію, перевіряти права доступу та логувати операції.

## 16. Користувацька частина

Користувацька частина орієнтована на швидке отримання інформації. Головна сторінка надає огляд сервісу, список АЗС і ключові елементи навігації. Сторінка цін дозволяє фільтрувати записи за містом, мережею АЗС і типом пального. Картки АЗС показують назву, адресу, фото, поточні ціни, доступні види пального та додаткову інформацію.

Пошук дозволяє швидко знайти потрібну мережу або адресу. Сортування за ціною допомагає знайти найдешевший варіант. Фільтри за типом пального корисні тому, що користувачі зазвичай цікавляться конкретним пальним, наприклад А-95 або дизелем. Історія цін дозволяє зрозуміти, чи була ціна стабільною або нещодавно змінилася.

Профіль користувача містить персональні дані, фото, підписки, можливість редагування та видалення акаунта. Підписки дозволяють користувачу обрати місто та тип пального, після чого система повідомляє про зміни. Це створює персоналізований сценарій використання: користувач не просто переглядає сайт, а отримує релевантні оновлення.

Коментарі та оцінки дають змогу збирати користувацький зворотний зв'язок щодо АЗС. Це доповнює цінові дані якісною інформацією: користувач може оцінити не лише дешевизну, а й сервіс, доступність, черги або якість обслуговування.

## 17. Аналітика, графіки та статистика

Аналітичний модуль LiveFuelMap призначений для перетворення сирих цінових записів на зрозумілу інформацію. Користувач може бачити не лише поточну ціну, а й історію її зміни. Це важливо, оскільки одноразове значення ціни не показує тенденцію.

Для графіків використовується **Chart.js** через React-обгортку. Chart.js - це JavaScript-бібліотека для побудови графіків, яка підтримує line charts, bar charts, tooltips, legends, responsive layout і взаємодію з користувачем. У LiveFuelMap графіки можуть показувати зміну ціни за датами, порівняння декількох АЗС, різницю між поточною та попередньою ціною, відсоток зміни та загальну динаміку.

Статистика в системі формується за такими показниками:

- середню ціну за містом;
- мінімальну та максимальну ціну;
- найдешевшу АЗС за типом пального;
- найдорожчу АЗС;
- відсоток зміни;
- кількість оновлень за період;
- порівняння мереж АЗС;
- історію зміни по конкретній станції.

Експорт даних дозволяє користувачу або адміністратору отримати звіт у файлі. Це корисно для подальшого аналізу, вставки в документи, звітності або архівування. API експорту приймає параметри фільтрації та повертає файл із відповідним `Content-Disposition`.

## 18. UX/UI-дизайн

UX/UI LiveFuelMap орієнтований на швидкість, зрозумілість і адаптивність. Для сервісу моніторингу цін важливо, щоб користувач не витрачав час на складну навігацію. Основні дані мають бути доступні за мінімальну кількість дій: відкрити сторінку, обрати тип пального, побачити ціну.

Tailwind CSS забезпечує єдину дизайн-систему: кольори, відступи, шрифти, стани hover/focus, адаптивні сітки. Компонентна архітектура дозволяє повторно використовувати картки, кнопки, таблиці, модальні вікна, бейджі, форми та повідомлення.

Темна тема покращує комфорт використання в умовах низького освітлення. Анімації роблять взаємодію плавнішою, але не повинні сповільнювати користувача. Модальні вікна використовуються для авторизації, профілю, підтверджень і редагування. Toast-повідомлення інформують про успіх або помилку без різкого переривання сценарію.

Доступність інтерфейсу враховується через контрастність, зрозумілі підписи, логічну навігацію, фокус-стани та достатній розмір інтерактивних елементів. Для таблиць важливо, щоб на мобільних пристроях вони не ламали layout, а перетворювалися на компактне або прокручуване відображення.

## 19. Оптимізація продуктивності

Продуктивність LiveFuelMap оптимізується на декількох рівнях. На frontend-рівні Vite формує оптимізовану production-збірку, розділяє модулі, мінімізує JavaScript і CSS. React-компоненти організовані так, щоб уникати зайвого дублювання логіки. Дані завантажуються через централізований API-шар, а контексти зберігають спільний стан.

На backend-рівні використовується асинхронна модель ASP.NET Core. Запити до БД виконуються через EF Core async API, що дозволяє ефективно використовувати потоки сервера під час I/O-операцій. Для read-запитів застосовується `AsNoTracking`, коли дані не потрібно змінювати, що зменшує overhead change tracker-а.

У реалізованій системі in-memory state використовується для idempotency-захисту повторних запитів і rate limiting, а продуктивність основних read-сценаріїв забезпечується індексами, серверною фільтрацією, пагінацією, `AsNoTracking` для read-only запитів та уникненням N+1-запитів. Для API обмежується обсяг відповідей, щоб frontend не отримував надмірні набори даних.

SignalR зменшує кількість зайвих HTTP-запитів. Замість polling-підходу, коли клієнт кожні декілька секунд питає сервер про зміни, сервер сам повідомляє клієнта про оновлення. Це знижує навантаження і покращує UX.

Rate limiting захищає API від надмірного навантаження. Idempotency для записуючих операцій запобігає випадковому дублюванню запитів при повторній відправці форми або нестабільному з'єднанні.

## 20. Тестування

Тестування LiveFuelMap поділяється на unit-тести та integration-тести. Unit-тести перевіряють окремі компоненти без повного запуску системи. Наприклад, тестуються нормалізація типів пального, визначення зміни ціни, BCrypt-хешування, генерація ключів JWT, логіка парсингу HTML і topic guard чат-бота.

Integration-тести перевіряють роботу API в умовах, наближених до реальних: запуск тестового сервера, HTTP-запити до endpoint-ів, авторизація, адмін-доступ, історія чату, публічні контролери. Такі тести важливі, тому що багато помилок виникає саме на межі між контролером, DI, EF Core, middleware та серіалізацією.

Тестування API включає:

- успішну реєстрацію та вхід;
- перевірку JWT;
- обмеження доступу до admin endpoint-ів;
- отримання публічних даних;
- роботу чат-історії;
- перевірку context-aware сценарію чат-бота;
- перевірку імпорту і історії цін;
- перевірку security-сервісів.

Для дипломного проєкту наявність тестів демонструє не лише працездатність, а й інженерну зрілість системи. Тести дозволяють безпечніше проводити рефакторинг, змінювати бізнес-логіку та додавати нові можливості.

Повноцінне production-навантаження для SignalR потребує окремого сценарію з багатьма одночасними клієнтами, але для дипломної реалізації перевірено базову працездатність hub-підключення.

## 20.2. Технічні складності, компроміси та прийняті рішення

Під час реалізації LiveFuelMap виникло декілька практичних технічних складностей. Їх вирішення вплинуло на архітектуру системи та дозволило зробити проєкт ближчим до реальної production-ready розробки.

Першою складністю стала нормалізація назв АЗС і типів пального. Зовнішні джерела використовують різні варіанти написання: кирилицю, латиницю, скорочення, дефіси, пробіли, службові рядки таблиць. Для вирішення цієї проблеми реалізовано `IFuelNormalizer`, словники alias-ів і стабільні fuel code. Це дозволило уникнути дублювання АЗС і забезпечити однакову роботу frontend, backend та парсера.

Другою складністю стала зміна структури зовнішніх HTML-сторінок. HTML-скрапінг є менш стабільним, ніж офіційний API, тому parser client реалізовано як окремий infrastructure-компонент. Якщо структура сайту зміниться, достатньо оновити конкретний client, не змінюючи бізнес-логіку імпорту, БД або REST API.

Третьою складністю була синхронізація автоматичного імпорту та ручних адміністративних корекцій. Для цього в `FuelPrice` використано поле `IsManual`. Якщо запис створено або змінено адміністратором, parser logic не повинен неконтрольовано перезаписувати ручну правку.

Четвертим компромісом стало використання локального AI. Чат-помічник не зроблено ядром системи, оскільки головна функція LiveFuelMap - моніторинг і аналіз цін. AI-модуль реалізовано як додатковий інтерфейс взаємодії з даними. Фактичні ціни отримуються з БД, а локальна модель використовується лише для формування природної відповіді в межах підготовленого контексту.

П'ятим компромісом є зберігання токенів у `localStorage` на frontend. Це зручне рішення для SPA, але воно вимагає сильного XSS-захисту. Тому в системі не використовується небезпечне вставлення HTML для користувацького контенту, access token має обмежений строк життя, а refresh token перевіряється та відкликається на backend.

Шостою складністю стала підтримка real-time оновлень без надмірного навантаження. Для цього SignalR використовується не для передачі великих наборів даних, а для подій про зміну. Повні дані frontend отримує через REST API, що зберігає чіткий розподіл відповідальності між REST і WebSocket-каналом.

## 21. Розгортання

LiveFuelMap підтримує локальне розгортання через скрипти та контейнеризацію через **Docker Compose**. Docker - це платформа контейнеризації, яка дозволяє запускати застосунок і його залежності в ізольованих середовищах. Docker Compose описує декілька сервісів: MySQL, Ollama для локального AI-чату та API-контейнер.

Переваги Docker для LiveFuelMap:

- однакова конфігурація середовища для розробника та сервера;
- швидкий запуск MySQL без ручного встановлення;
- ізоляція залежностей;
- простіше масштабування;
- можливість переносити систему між машинами;
- контроль версій сервісів.

Конфігурація системи зберігається в `appsettings.json`, `appsettings.Development.json`, змінних середовища та `.env`. Це дозволяє не зберігати секрети в коді, а задавати їх окремо: JWT secret, connection string, порти, endpoint-и зовнішніх сервісів, параметри AI, parser interval, rate limit, idempotency.

Типовий сценарій запуску:

1. Налаштувати `.env`.
2. Запустити MySQL або Docker Compose.
3. Виконати EF Core migrations.
4. Зібрати frontend через Vite.
5. Запустити ASP.NET Core API.
6. Відкрити вебсервіс у браузері.

У production-сценарії frontend може збиратися у статичні файли `dist`, після чого ASP.NET Core віддає їх як static files. API та frontend можуть працювати як один deployable unit або бути розділеними сервісами.

## 22.1. Економічна оцінка ефективності

Економічна ефективність LiveFuelMap полягає в автоматизації процесу, який у ручному режимі потребує значно більше часу. Без централізованого сервісу користувач відкриває декілька сайтів АЗС або агрегаторів, шукає своє місто, обирає тип пального, порівнює ціни, перевіряє актуальність і вручну робить висновок. LiveFuelMap скорочує цей процес до одного інтерфейсу з фільтрами, сортуванням і графіками.

Для звичайного водія економія часу проявляється в тому, що перевірка ціни займає не 5-10 хвилин ручного перегляду різних джерел, а декілька секунд у вебінтерфейсі. Якщо користувач перевіряє ціни хоча б 2-3 рази на тиждень, централізований сервіс економить приблизно 30-60 хвилин на місяць. Для компанії з автопарком ефект більший, оскільки рішення про заправку приймаються частіше та впливають на регулярні витрати.

Для адміністратора або аналітика автоматизація вебскрапінгу зменшує потребу в ручному внесенні цін. Наприклад, якщо зовнішнє джерело містить 50-100 записів, ручне перенесення таких даних у таблицю може займати 20-40 хвилин, тоді як parser worker у локальному тесті обробив 53 записи приблизно за 1 секунду. Навіть з урахуванням перевірки якості даних автоматизований підхід значно зменшує операційні витрати.

Економічна користь також пов'язана з якістю рішень. Якщо користувач бачить мінімальну, середню та історичну ціну, він приймає рішення не на основі випадкової інформації, а на основі структурованих даних. Для бізнесу це означає можливість планувати витрати на пальне, аналізувати динаміку та зменшувати ризик переплати.

LiveFuelMap також створює основу для подальшої монетизації або прикладної інтеграції: API-токени для сторонніх сервісів, звіти для бізнесу, підписки на оновлення, аналітичні dashboard-и та майбутні прогнозні модулі. У межах дипломного проєкту економічна частина демонструє, що система має не лише навчальну, а й практичну цінність.

## 23. Можливості масштабування

Архітектура LiveFuelMap передбачає подальше масштабування. На рівні frontend можна додавати нові сторінки, компоненти, карти, мобільні сценарії та PWA-функції без зміни backend-ядра. На рівні backend можна додавати нові контролери, сервіси, джерела парсингу, background workers та інтеграції.

Масштабування backend можливе горизонтально: декілька API-інстансів можуть працювати за reverse proxy або load balancer. Для SignalR у масштабованому середовищі можна використати backplane, наприклад Redis. Для кешування популярних запитів також доцільно додати Redis. Для великих обсягів історії цін можна запровадити архівування, партиціювання таблиць за датою або перенесення аналітичних агрегатів в окремі materialized views.

Система парсингу може масштабуватися через розділення джерел за worker-ами. Наприклад, окремий worker може обробляти один регіон або одну групу джерел. Для уникнення одночасного запуску однакових задач у distributed-середовищі доцільно використовувати distributed lock.

API для сторонніх сервісів може бути розширений через API-токени зі scopes, ліміти, usage metrics і білінг. Це дозволить LiveFuelMap працювати не лише як користувацький сайт, а й як data provider для інших продуктів.

## 24. Перспективи подальшого розвитку

Подальший розвиток LiveFuelMap може включати такі напрями:

- **Мобільний застосунок.** Створення застосунку для Android та iOS на React Native або Flutter дозволить користувачам отримувати ціни, push-повідомлення і рекомендації безпосередньо на смартфоні.
- **AI-аналітика.** Інтеграція AI-модулів може допомогти пояснювати зміну цін, знаходити аномалії, формувати короткі аналітичні звіти та відповідати на природномовні запити користувачів.
- **Прогнозування цін.** На основі історії цін, курсу валют, сезонності та зовнішніх факторів можна побудувати модель прогнозування вартості пального.
- **Карти та геолокація.** Інтеграція карт дозволить показувати АЗС поруч із користувачем, будувати маршрути, оцінювати відстань і фактичну вигоду від поїздки до дешевшої АЗС.
- **Персональні рекомендації.** Система може враховувати улюблені мережі, тип пального, місцезнаходження, історію переглядів і підписки користувача.
- **Розширення кількості АЗС.** Додавання нових мереж підвищить повноту даних і практичну цінність сервісу.
- **Розширення кількості міст.** Сервіс може масштабуватися з одного регіону до всієї України.
- **API для сторонніх сервісів.** Документований public API дозволить інтегрувати LiveFuelMap у навігаційні сервіси, CRM, логістичні системи або мобільні застосунки.
- **Покращення системи сповіщень.** Можна додати push-повідомлення, Telegram-бота, SMS або налаштовувані пороги зміни ціни.
- **Покращення аналітики.** Варто додати heatmap цін, порівняння регіонів, прогнозні графіки, експорт у BI-формати та агреговані dashboard-и.
- **SEO-оптимізація.** Для публічних сторінок можна додати server-side rendering або prerendering, Open Graph metadata, sitemap і структуровані дані.
- **Покращення безпеки.** Доцільно додати two-factor authentication, audit log, device sessions і granular permissions.

## 25. Висновки

У результаті виконання дипломного проєкту було розроблено вебсервіс LiveFuelMap, який вирішує актуальну задачу централізованого моніторингу цін на пальне. Система автоматизує збір даних із зовнішніх джерел, нормалізує їх, зберігає в реляційній базі даних, надає доступ через REST API, відображає інформацію в сучасному адаптивному інтерфейсі та підтримує оновлення в реальному часі.

Проєкт має повноцінну багаторівневу архітектуру: React/Vite frontend, ASP.NET Core Web API backend, BLL-рівень бізнес-логіки, DAL-рівень з Entity Framework Core, Infrastructure-рівень для парсингу, email, JWT, логування і background worker-ів, а також MySQL як основне сховище даних. Таке розділення забезпечує підтримуваність, тестованість і можливість подальшого масштабування.

Використання вебскрапінгу дозволяє автоматизувати оновлення цін, а REST API забезпечує стандартизовану взаємодію між клієнтом і сервером. SignalR розширює систему real-time функціональністю, JWT і BCrypt забезпечують базовий рівень безпеки, а role-based authorization відокремлює звичайні користувацькі сценарії від адміністративних.

З погляду користувача LiveFuelMap є зручним інструментом для пошуку, порівняння та аналізу цін на пальне. З погляду адміністратора - це система керування даними, джерелами, користувачами та якістю інформації. З погляду інженерної реалізації - це сучасний full-stack проєкт, який демонструє практичне застосування REST API, вебскрапінгу, реляційних баз даних, авторизації, real-time комунікації, компонентної frontend-архітектури та автоматизованого тестування.

## Коротке пояснення проєкту для усного захисту

Мій дипломний проєкт називається LiveFuelMap. Це вебсервіс для моніторингу цін на пальне, який дозволяє користувачам переглядати актуальні ціни на бензин, дизельне пальне та газ у різних мережах АЗС. Основна проблема, яку вирішує система, полягає в тому, що ціни на пальне часто змінюються, а інформація розміщена в різних джерелах. Користувачу незручно вручну перевіряти багато сайтів, тому LiveFuelMap централізує ці дані в одному інтерфейсі.

Система складається з frontend-частини на React, backend-частини на ASP.NET Core Web API та бази даних MySQL. Frontend відповідає за інтерфейс: сторінки, картки АЗС, таблиці, фільтри, графіки, профіль користувача, адмін-панель і модальні вікна. Backend реалізує REST API, авторизацію, бізнес-логіку, роботу з базою даних, вебскрапінг, логування та оновлення в реальному часі через SignalR.

Дані потрапляють у систему через фоновий парсер. Він періодично звертається до зовнішніх джерел, отримує HTML або JSON, витягує ціни, нормалізує назви АЗС і типи пального, перевіряє коректність записів і зберігає їх у базу даних. Якщо ціна змінилася, система фіксує це в історії та надсилає real-time повідомлення клієнтам.

Для безпеки використовується JWT-авторизація, refresh tokens, BCrypt-хешування паролів, email-верифікація та рольова модель доступу. Звичайний користувач може переглядати ціни, керувати профілем і підписками, а адміністратор має доступ до керування користувачами, АЗС, джерелами даних, API-токенами та запуском парсера.

Особливістю проєкту є те, що він не просто показує поточні ціни, а зберігає історію, дозволяє будувати графіки, порівнювати АЗС, аналізувати зміну вартості та підписуватися на оновлення. У майбутньому систему можна розширити мобільним застосунком, AI-аналітикою, прогнозуванням цін, інтеграцією карт і геолокації, а також відкритим API для сторонніх сервісів.
